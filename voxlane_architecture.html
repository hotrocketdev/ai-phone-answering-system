Product Requirements Document

v1.0 MVP UK Market Restaurants + Local Business

1. Executive Summary

VoxLane is a B2B SaaS platform that deploys an AI-powered voice receptionist for restaurants and local businesses in the United Kingdom. The platform answers inbound telephone calls in real time, conducts natural human-like conversations, manages bookings via direct API integration with reservation systems (initially ResDiary), and escalates to human staff when required.

The core value proposition is: "Never miss another booking call."

Market Opportunity: UK restaurants collectively miss an estimated 30–40% of inbound calls during peak hours, evenings, and weekends. Each missed call represents £30–£120 in lost revenue. A single busy London restaurant takes 200+ calls per week.

2. Problem Statement

Missed Calls

Staff cannot answer every call during peak service. Calls during dinner service go straight to voicemail and are never returned.

After-Hours Bookings

Restaurants are closed but callers want to book. No answer = booking made at a competitor.

Staff Cost

Hiring dedicated phone staff is expensive. Existing staff are pulled away from service to answer routine booking calls.

Data Fragmentation

No analytics on inbound call volume, peak times, booking conversion rates, or common questions.

3. Goals & Non-Goals

MVP Goals

  • Answer 100% of inbound calls with a natural AI voice within 3 rings
  • Handle booking, modification, and cancellation workflows end-to-end
  • Answer restaurant FAQs (hours, location, menus, parking)
  • Transfer calls to human staff on request or escalation triggers
  • Send SMS confirmation to caller after booking actions
  • Integrate directly with ResDiary booking API
  • Provide call analytics dashboard to restaurant owners
  • Support multi-location restaurant groups (multi-tenant)

MVP Non-Goals

  • POS integration (Lightspeed, Square, etc.)
  • Payment processing
  • Outbound calling campaigns
  • Multi-language support (English only in MVP)
  • WhatsApp / web chat integration
  • AI-generated menu recommendations

1. Design Philosophy

Core Rule: The AI owns zero business state. It is a conversation orchestrator that calls server-side tools. All booking state, availability, and validation lives in backend services. This prevents hallucination of availability, invented confirmations, and race conditions.

Realtime Voice Architecture

GoOpenAI Realtime APITwilio Media Streams

Audio Pipeline

Key insight: Twilio delivers audio as µ-law (G.711) 8kHz 8-bit mono. OpenAI Realtime expects PCM 16-bit 24kHz. The Go engine must transcode bidirectionally with zero-copy buffers to avoid GC pressure.

Caller Audio Path (Inbound):
  Twilio → WebSocket → Go
    ↳ Receive mulaw-8kHz frames (20ms chunks)
    ↳ Decode mulaw → linear PCM
    ↳ Upsample 8kHz → 24kHz (linear interpolation)
    ↳ Convert 8-bit → 16-bit signed
    ↳ Forward to OpenAI Realtime API (input_audio_buffer.append)

AI Audio Path (Outbound):
  OpenAI → Go → Twilio
    ↳ Receive response.audio.delta (PCM 24kHz 16-bit)
    ↳ Downsample 24kHz → 8kHz
    ↳ Encode PCM → mulaw
    ↳ Base64 encode
    ↳ Send via WebSocket media.write to Twilio

Barge-In / Interruption Handling

When a caller speaks while the AI is talking, the system must immediately stop audio playback and process the interruption.

  1. OpenAI Realtime API fires input_audio_buffer.speech_started event
  2. Go handler immediately sends response.cancel to OpenAI
  3. Go sends {"event":"clear","streamSid":"..."} to Twilio to flush audio buffer
  4. Any queued audio frames are dropped (checked via sequence number)
  5. OpenAI begins processing the new speech input

Result: Interruption is handled in <100ms. The caller feels heard immediately.

Voice Activity Detection (VAD)

OpenAI Realtime API handles server-side VAD with configurable silence thresholds. For restaurant calls:

ParameterValueReason
turn_detection.typeserver_vadLet OpenAI handle VAD for simplicity and reliability
turn_detection.threshold0.5Medium sensitivity — balanced for restaurant background noise
turn_detection.silence_duration_ms700msNatural pause without cutting off hesitant callers
turn_detection.prefix_padding_ms300msCapture the start of speech reliably

Silence & Hang-up Detection

  • After 8s of silence with no speech: AI plays a soft prompt ("Are you still there?")
  • After 15s total silence: AI politely closes the call
  • Twilio disconnect event on WebSocket triggers immediate session cleanup
  • All sessions have a 30-minute hard TTL in Redis

Tool Call Flow

OpenAI fires: response.function_call.arguments
  ↓
Go toolHandler receives: { name: "check_availability", arguments: {...} }
  ↓
Go validates tool is allowed in current state (state machine guard)
  ↓
Go HTTP POST to NestJS: /internal/tools/:toolName
  Headers: X-Session-ID, X-Tenant-ID, X-Tool-Signature (HMAC)
  ↓
NestJS validates signature + tenant context
  ↓
NestJS executes tool (ResDiary call, DB query, etc.)
  ↓
NestJS returns JSON result (or structured error)
  ↓
Go sends: conversation.item.create (type: function_call_output)
  ↓
OpenAI continues conversation with real data injected

Tool Call Security

  • All tool calls are HMAC-signed with a shared secret per tenant
  • NestJS validates signature before executing any tool
  • Tools are scoped to the tenant — a tool call from tenant A cannot access tenant B's bookings
  • Tool call rate limiting: max 10 tool calls per session to prevent runaway loops
  • Tool timeout: 3s max — if backend doesn't respond, tool returns a graceful error message

Dead Letter Handling

  • Failed jobs after max retries move to failed state in BullMQ
  • Bull Board dashboard provides visibility at /admin/queues (internal only)
  • SMS failures trigger fallback: email notification to restaurant manager
  • ResDiary sync failures create a manual reconciliation task for staff dashboard
  • Critical queue failures (3+ consecutive) trigger PagerDuty alert

Horizontal Scaling Concern

Critical: Twilio Media Streams maintain a WebSocket connection to a specific server. When scaling horizontally, load balancer MUST use sticky sessions (IP hash or session cookie) to ensure the same Go instance handles all messages for a given call. Redis-backed session state means any Go node can read the context, but the live WebSocket must be on the same node.

Conversation State Machine

8 StatesDeterministic Transitions

Design Rule: Each state loads a minimal, focused system prompt extension. The base system prompt is tiny. State-specific context is injected only when needed. This dramatically reduces token usage and prevents the AI from wandering.

States

Greeting
Initial call answer. AI introduces itself and detects intent.
→ Booking, ModifyBooking, Cancellation, FAQ, Complaint, HumanTransfer
Booking
Collect name, date, time, party size. Check availability. Confirm reservation.
→ Closing, HumanTransfer
ModifyBooking
Find existing booking by phone/name/ref. Collect changes. Update via tool.
→ Closing, HumanTransfer
Cancellation
Locate booking. Confirm cancellation intent. Execute cancellation tool.
→ Closing, HumanTransfer
Complaint
Listen empathetically. Capture details. Log complaint. Offer transfer.
→ HumanTransfer, Closing
FAQ
Retrieve FAQ answer from tool. Answer question. Detect follow-up intent.
→ Greeting, Booking, Closing
HumanTransfer
Acknowledge transfer request. Warm-transfer to SIP number. Notify staff.
→ [Call ends]
Closing
Summarise what was done. Confirm SMS sent. Polite farewell.
→ [Call ends]

Transition Rules

Multi-Tenant Architecture

Shared InfrastructureData Isolation

Isolation Model

VoxLane uses a shared infrastructure, data-isolated multi-tenant model. All tenants share the same application code and infrastructure, but data is rigorously isolated via:

  • Supabase RLS: Every table has a policy USING (tenant_id = auth.jwt() ->> 'tenant_id')
  • Application-level tenancy: Every API request extracts tenant_id from JWT and passes it to all service calls
  • Redis key namespacing: All Redis keys prefixed with tenant:{tenantId}:
  • Encryption key isolation: Each tenant has a unique data encryption key (DEK) managed via AWS KMS / Vault

Tenant Configuration

Each tenant (restaurant group) contains one or more locations. Each location has independent configuration:

Authentication

ResDiary uses OAuth 2.0 client credentials flow. Each tenant's ResDiary API key is stored encrypted in Supabase Vault. Access tokens are cached in Redis per tenant (TTL: token expiry - 60s) to avoid token refresh on every tool call.

// ResDiary token management
class ResdiartyAuthService {
  async getAccessToken(tenantId: string): Promise<string> {
    const cacheKey = `resdiary:token:${tenantId}`;
    const cached = await redis.get(cacheKey);
    if (cached) return cached;

    const creds = await this.vaultService.getCredentials(tenantId, 'resdiary');
    const token = await this.fetchOAuthToken(creds);
    
    await redis.setex(cacheKey, token.expires_in - 60, token.access_token);
    return token.access_token;
  }
}

Audio Transcoding (Go)

// Go audio pipeline — zero-copy buffer design
func (s *Session) handleTwilioMedia(payload []byte) {
    // 1. Decode base64
    mulaw := base64.Decode(payload)
    
    // 2. Decode µ-law → signed 16-bit PCM (lookup table, O(1) per sample)
    pcm8k := decodeMulaw(mulaw)
    
    // 3. Upsample 8kHz → 24kHz (3:1 linear interpolation)
    pcm24k := upsample8to24(pcm8k)
    
    // 4. Send to OpenAI Realtime API
    s.openaiWS.Write(inputAudioAppend(pcm24k))
}

func (s *Session) handleOpenAIAudio(pcm24k []byte) {
    // 1. Downsample 24kHz → 8kHz  
    pcm8k := downsample24to8(pcm24k)
    
    // 2. Encode PCM → µ-law
    mulaw := encodeMulaw(pcm8k)
    
    // 3. Base64 encode
    encoded := base64.Encode(mulaw)
    
    // 4. Send to Twilio
    s.twilioWS.Write(mediaWrite(encoded, s.streamSid))
}

WebSocket Connection Management

  • Go uses gorilla/websocket with read/write goroutine separation per connection
  • Ping/pong heartbeat every 30s to detect stale connections
  • Write timeout: 5s — if Twilio doesn't ACK, close and cleanup
  • Max connections per Go instance: 500 concurrent (memory-bound: ~25MB per session including audio buffers)
  • Connection pool shared between Twilio WS and OpenAI WS per session

SIP Transfer Implementation

Twilio VoiceWarm Transfer

Transfer Mechanism

VoxLane uses Twilio's warm transfer pattern: the AI stays on the line briefly while the destination phone rings, then bridges the caller when staff answers. If no answer, AI can take a message instead.

// NestJS transfer_to_human tool handler
async transferToHuman(params: TransferParams): Promise<ToolResult> {
  const location = await this.tenantService.getLocation(params.locationId);
  
  // 1. Update Twilio call with new TwiML via REST API
  await this.twilioClient.calls(params.callSid).update({
    twiml: `<Response>
      <Say voice="alice">Please hold while I connect you to our team.</Say>
      <Dial timeout="30" 
            action="/voice/transfer-complete/${params.sessionId}"
            method="POST">
        <Number statusCallbackEvent="initiated ringing answered completed"
                statusCallback="/voice/transfer-status">
          ${location.transferNumber}
        </Number>
      </Dial>
      <Say>I'm sorry, our team is unavailable. Let me take a message.</Say>
      <Redirect>/voice/take-message/${params.sessionId}</Redirect>
    </Response>`
  });
  
  // 2. Send context SMS to staff
  await this.smsService.sendStaffAlert(location.transferNumber, {
    callerName: params.context.callerName,
    intent: params.context.intent,
    summary: params.context.summary
  });
  
  // 3. Mark session as transferring
  await this.sessionService.updateState(params.sessionId, 'HumanTransfer');
  
  return { success: true, message: "Transferring now" };
}

Optimisation Techniques

1. State-Scoped Tool Schema

Only include tool definitions for tools valid in the current state. In Greeting state, send 1 tool definition (~70 tokens). In Booking state, send 3 (~210 tokens). Never send all 10 tools at once.

2. Compact Tool Responses

// Bad — verbose tool response (400 tokens):
{
  "status": "success",
  "data": {
    "venue": { "id": "RD-1234", "name": "The Oak Room", "address": "...", ... },
    "reservation": { "id": "...", "date": "2025-06-14", "time": "19:30", ... },
    "confirmation": { "email": true, "sms": false },
    ...
  }
}

// Good — minimal tool response (80 tokens):
{
  "success": true,
  "booking_ref": "RD-12345",
  "date": "Saturday 14th June",
  "time": "7:30 PM",
  "covers": 4
}

3. Conversation Context Pruning

OpenAI Realtime maintains its own conversation history. For sessions exceeding 15 turns, inject a context summary replacing the early conversation: "Summary so far: Caller Sarah booked a table for 4 on Friday 14th June at 7:30pm. Now asking about parking."

4. FAQ Short-Circuit

Common FAQs (hours, address, parking) are served from Redis without AI involvement. The Go engine detects simple FAQ patterns via keyword matching and injects the pre-written answer directly as a tool result — bypassing AI generation for purely factual answers.

5. Temperature Optimisation

Temperature 0.6 balances naturalness with predictability. Booking confirmation steps use temperature 0.4 (highly reliable structured output). General chat uses 0.7 (more natural-sounding).

AI Prompt Architecture

State-Driven PromptsAnti-Hallucination

Prompt Composition Model

Final system prompt = BASE_PROMPT + STATE_PROMPT[currentState] + TENANT_CONTEXT

// Assembled in Go before session.update or state transition

BASE_PROMPT (static, ~150 tokens)

You are a professional AI voice receptionist for a restaurant.
Your name is {ai_name}. You speak naturally, warmly, and concisely.

CORE RULES:
- Never invent availability, prices, or booking details. Always use tools.
- If a tool fails twice, transfer to a human without apologising excessively.
- Be concise. Spoken responses should be under 3 sentences unless explaining options.
- Respond ONLY to restaurant-relevant queries.
- Never discuss AI, technology, or how you work.
- Today is {current_date}. Current time is {current_time} UK time.

STATE_PROMPTS (injected on state entry)

// Greeting state
"Greet the caller warmly. Your restaurant is {restaurant_name}.
Listen for their intent: new booking, existing booking change/cancel, question, or complaint.
Do not assume intent — ask if unclear."

// Booking state  
"Collect: caller's name, party size (1-{max_party}), preferred date and time.
Use check_availability before confirming any slot.
Confirm all details clearly before calling create_booking.
Once booked, say the booking reference and offer SMS confirmation."

// ModifyBooking state
"Find the booking first using find_booking with caller's phone or name+date.
Confirm which booking before making any changes.
Collect the new date/time/party size.
Check availability for the new slot before modifying."

// Complaint state
"Listen with empathy. Do not argue or make promises about compensation.
Summarise what you've heard back to the caller.
Offer to connect them with the manager or note their feedback for follow-up.
Do not say the problem will definitely be fixed — say it will be reviewed."

TENANT_CONTEXT (per-restaurant, injected once)

{
  restaurant_name: "The Oak Room",
  ai_name: "Olivia",
  address: "12 High Street, London SW1A 1AA",
  phone_display: "020 7123 4567",
  today_hours: "12:00 PM to 10:30 PM",
  tomorrow_closed: false,
  max_party_size: 12,
  special_note: "We are fully booked on Saturday 15th June — do not check availability for that date."
}

Anti-Prompt-Injection

Caller speech is processed as audio (not text). The OpenAI Realtime API transcribes internally. However, as a defence-in-depth measure, all tool call arguments are validated server-side — any attempt to inject SQL, override tool parameters, or supply adversarial dates/names is sanitised before reaching the database or ResDiary API.

Scaling Triggers

  • Add VPS node: When active_voice_sessions routinely exceeds 60% of capacity
  • Redis Sentinel → Cluster: When Redis memory exceeds 16GB or ops/sec > 50k
  • Migrate to K8s: When managing >5 VPS nodes becomes operationally complex, or when needing auto-scaling
  • Multi-region: When expanding to non-UK markets with >100ms latency to UK endpoints

Go Voice Engine Horizontal Scaling

Each Go instance handles up to 500 concurrent WebSocket connections (voice sessions). To scale to 2,000 concurrent calls, deploy 4 Go instances behind an L4 load balancer with consistent hashing on CallSid for sticky sessions. All session state in Redis is instance-agnostic.

Critical K8s Considerations

  • Sticky sessions for WebSocket: Use NGINX Ingress with nginx.ingress.kubernetes.io/affinity: cookie to pin Twilio Media Stream WebSockets to a specific pod
  • Pod Disruption Budget: Minimum 1 voice-engine pod always running — prevents simultaneous pod evictions during updates
  • Graceful shutdown: Go voice engine catches SIGTERM, stops accepting new connections, waits for active sessions to complete (30s drain timeout), then exits
  • Redis on K8s vs managed: Use managed Redis (Upstash, Elasticache) rather than Redis on K8s — stateful workloads on K8s add operational complexity

Zero-Downtime Deployment Strategy

Services deployed with Docker's rolling update approach. The Go voice engine uses a graceful drain: new container starts on alternate port, load balancer switches traffic once health check passes, old container drains active sessions (up to 30s), then stops.

Phase 2 Analytics (Month 4–9)

  • Sentiment Analysis: Post-call DeepSeek analysis of transcript to classify caller satisfaction (positive / neutral / frustrated). Trend over time.
  • Booking Pattern Intelligence: Which times/dates are most requested but unavailable — helps restaurants optimise their opening hours and seating.
  • Complaint Categorisation: Auto-classify complaints into categories (food quality, service, wait time, etc.) using DeepSeek V4.
  • Call Transcript Search: Full-text search over call transcripts for operational review.

Phase 3 Analytics (Month 10+)

  • Revenue Attribution: Link booking calls to table spend data (via POS integration) — show revenue per AI-answered call.
  • Predictive Insights: Forecast busy periods from historical call patterns + external data (events, weather). Recommend staffing changes.
  • Benchmarking: Anonymous peer comparison — "Your booking conversion rate is 74%, above the 68% average for similar restaurants."
  • AI Weekly Digest: Auto-generated weekly summary email to restaurant managers using DeepSeek (highlights, anomalies, recommendations).
  • Voice of Customer Reports: Monthly AI-generated report summarising common themes from calls, complaints, and FAQs.

Analytics Architecture (Phase 2+)

Call ends
  → BullMQ analytics-events queue
  → Worker: enrichment job (DeepSeek analysis on transcript)
  → Structured event written to Supabase analytics tables
  → Supabase real-time subscription → Dashboard live update
  → Hourly aggregation job: aggregate to call_analytics_hourly
  → Daily: generate daily report (DeepSeek) → email to manager
  → Weekly: AI digest generated → email + in-dashboard notification

Analytics Cost Management: DeepSeek V4 at ~$0.0005/1K tokens means a full call transcript analysis (~2,000 tokens) costs ~$0.001. Daily report generation (~5,000 tokens) costs ~$0.0025. Monthly analytics cost per tenant is pennies — not a cost driver.
